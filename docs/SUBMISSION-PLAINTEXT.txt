TAGLINE
================================================================

Approve your AI agent's payments by replying to an email. Arc verifies Google's signature on-chain.


================================================================
PROJECT BRIEF (short description)
================================================================

Fala gives an AI agent a vault it can spend from on its own, up to limits you set. Anything bigger becomes a request that arrives as an ordinary email. You reply "approve" from Gmail, and that reply IS the signature. The Fala contract holds Google's public DKIM key and verifies the RSA-2048 signature on your reply directly on-chain, with no zero-knowledge circuit, for about a cent on Arc, before any money moves.

No wallet app. No seed phrase. No dashboard for the human. If you can reply to an email, you can approve a payment.

A prompt-injected agent can write any email it wants. It cannot make Google sign one from you.

DETAILED DESCRIPTION
================================================================


THE PROBLEM

Every tool builds its own front door. A dashboard to check, an app to install, an extension to approve in, a wallet to sign with. Each one assumes you will come to it.

Now give an AI agent a budget. There are two options, and both are bad:

- Give it a card. It spends without asking. You find out afterwards.
- Put a human in front of a wallet. Every purchase needs someone to open an app, read a hex string, and sign. The agent's speed is gone.

So most teams let agents do everything except spend money. The blocker is not capability. It is consent. There is no way for a human to say "yes, that one" that is both fast and safe.

Meanwhile, one interface was never fragmented. Around 4.6 billion people use email, sending roughly 376 billion messages a day. Nobody needs onboarding to reply to an email. And agents already live in the inbox, because the invoices, quotes and confirmations they act on arrive there. The channel is already shared. It was simply never used for the one thing that matters: permission.


WHAT FALA DOES

An agent gets a vault with an automatic allowance. Under the limit, it just pays. Over the limit, it has to ask, and asking means an email to you.

1. The agent calls request(payee, amount, memo). Within its allowance and to a known payee, it is paid instantly.

2. Otherwise the vault stores an intent with a binding code and emits IntentCreated. The relay emails the approver.

3. The email's buttons open a reply with the subject already filled in, for example: FALA APPROVE 42 7f3a9c1b. The human presses Send.

4. Gmail DKIM-signs that reply on the way out. The relay verifies the signature locally, dry-runs checkEmail so no gas is wasted on junk, then submits approveByEmail.

5. The contract recomputes sha256 of the signed header block, verifies Google's RSA signature against the registered key, and requires that From equals the approver, that the From domain equals the signing domain, that the subject code matches this exact intent, and that the signing time is fresh. Then it pays.

Only header lines inside the block Google signed are trusted. Never the body. Never anything the relay adds. The relay cannot alter the payee or the amount, because both come from the intent already stored on-chain.


WHY THIS IS SAFE

The security argument is one sentence: a prompt-injected agent can write any email it wants, but it cannot make Google sign one from you.

The signature is produced by Google's DKIM private key, at send time, over your headers. The contract holds Google's public key and does the RSA-2048 verification itself, inside the transaction. This is zk-email without the zk: no circuits, no prover, no trusted setup.

Failed verification reverts with a named error, and each one has a test behind it: BadSignature, FromNotApprover, DomainMismatch, CodeMismatch, IntentNotPending, StaleTimestamp, SubjectMalformed, DuplicateHeader, MissingHeader, DkimNotLast, HeaderNotSigned, WrongAlgorithm, WrongCanonicalization, UnknownKey, KeyRevoked, KeyNotActive, Frozen, IntentExpired. Replay, header injection, cross-vault reuse and key-rotation attacks are each refused by name.


WHY ARC

Fala is only possible because of what Arc makes cheap.

RSA-2048 on the modexp precompile. One approval costs 533,230 gas, about 0.011 USDC, measured on-chain with a real Gmail message. That is what makes direct signature verification viable where a zero-knowledge circuit would otherwise be required. On a chain with ordinary gas economics, this design simply would not ship.

USDC is the gas token. The thing you approve and the thing that pays the fee are the same unit. There is no second token to hold and no swap between approving and paying, which matters enormously when the user is a person in an inbox who has never held crypto.

Deployment is cheap enough to give every user their own contract. A vault costs 0.1116 USDC to deploy, so per-user isolation is the default rather than a premium tier.

Fast finality lets the "Payment sent" receipt land in the same email thread while the person is still reading it.


HOW ARC STUDIO WAS USED

The contracts were written locally, then taken through Arc Studio for review and deployment. Studio project 7b5f36e6-a2d1-4ccc-b925-f3cf4a4bd39b. Three runs, with the exact prompts and full transcripts committed in the repo under prompts/ and docs/studio-runs/.

Run 1, review and harden. Studio ran the Foundry suite plus a Slither and manual security review, focused on header parsing, replay, code binding, the key-registry timelock, reentrancy and payout-failure handling. It fixed real findings and added 22 regression tests, taking the suite from 41 to 63 passing. Findings are written up in SECURITY_REVIEW.md.

Run 2, deploy to testnet. Studio rebuilt, reran the suite, and deployed with the owner passed explicitly as a constructor argument rather than defaulting to the deployer.

Run 3, verify. Studio confirmed owner() on-chain, confirmed that approverHash equalled the keccak256 of the lowercased approver address, and reported the exact strings subjectFor returns so the email templates could not drift from the contract.

One moment is worth recording. In run 2, Studio refused to deploy. The platform masked the approver address in what it could see, so it received the literal text [REDACTED_EMAIL], and it would not guess a value that gets hashed into the constructor and cannot be changed afterwards without an owner transaction. It stopped and asked. That is the behaviour you want from a tool that holds a deploy key.

Sign in with Google, and an embedded wallet is created for you. Create a vault, which is a real contract deployment and not a database row. Fund it in USDC. Connect an agent and set its ceiling: per payment, per day, and a largest-request line it cannot even ask above. From then on the human does nothing until an email arrives.


HONEST LIMITS

Privacy. The approval transaction carries email headers (From, To, Subject, Date) in calldata, readable by anyone. Use a dedicated Gmail. The message body is never sent on-chain.

Gmail only. The From domain must equal the DKIM signing domain, which limits approvers to Gmail addresses today.

Key rotation. Google rotates DKIM keys. New keys go through a timelock and old keys can be revoked instantly. If Google rotates before a new key is registered, approvals fail closed rather than open.

Trust in Google. Whoever controls Google's DKIM private key can sign approvals.

Account takeover. If someone owns your Gmail they can approve. The hard cap bounds the damage per request, and FALA FREEZE works from any device you still control.

Not audited. Small amounts only.


WHAT IS NEXT
